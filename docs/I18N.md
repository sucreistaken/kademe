# Kademe i18n

Two locales: `tr` and `en`. Both sides of the product ship in both.

## Two different problems, two mechanisms

**Template content** (question text, stage names, choice labels, consent copy)
is *data*. It lives in the database as `jsonb {tr, en}` and is selected with
`pickText(value, locale)` from `@/lib/candidate-safe`. Nothing here goes through
next-intl: a manager writing a question in the builder is authoring content, not
translating an interface.

**Interface text** (buttons, hints, error messages, empty states) is *source*.
It lives in JSON dictionaries and goes through next-intl.

## Layout

```
src/i18n/
  locale.ts                     LOCALES, Locale, DEFAULT_LOCALE, isLocale,
                                localeFromAcceptLanguage
  dates.ts                      shortDate / dateTime, locale aware
  candidate.ts                  loads the candidate dictionaries, candidateT()
  candidate-client.ts           useT(), the typed hook for client components
  messages/
    candidate.tr.json           source of truth for the candidate key set
    candidate.en.json           mirrors it, key for key
    manager.tr.json             the manager shell: nav, and the words every
    manager.en.json             screen shares
    settings.tr.json            the settings and audit screens
    settings.en.json
    screens.tr.json             dashboard, positions, candidates, compare,
    screens.en.json             library, review
  manager.ts                    merges the three, managerT()
  manager-client.ts             useMT(), the typed hook
  manager-locale.ts             managerLocale(), reads the kademe-lang cookie
```

One file **per surface per locale**, rather than one big file split by a
top-level `candidate` / `manager` key. The manager side is split three ways again
and merged at the top level in `src/i18n/manager.ts`, because several people edit
this panel at once and a single file means one of them silently overwrites the
other's strings. Namespaces stay unique across the three, so a caller writes
`t("settings.title")` without knowing which file it came from. Two reasons:

1. The provider ships only the strings the page actually renders. A candidate
   never downloads the manager panel's dictionary.
2. The key you read in the code is the key you find in the file. `t("intro.start")`
   lives at `intro.start`, with no prefix to remember.

## Key naming

`<screen>.<thing>`, camelCase, no sentence fragments as keys.

```json
{
  "intro": { "start": "Başla", "consentRequired": "Başlamak için ..." },
  "errors": { "STAGE_EXPIRED": "Bu aşamanın süresi doldu." }
}
```

`errors` is keyed by the API error code, so a route handler can answer with
`message(locale, "STAGE_EXPIRED")` and the client can render the string it was
given without a lookup table of its own.

Placeholders use ICU: `"minutes": "{count} dk"`. A message that wraps part of
itself in a link uses ICU tags and `t.rich`:

```json
"contactHint": "Bir sorun olduğunu düşünüyorsan <mail>{email}</mail> adresine yazabilirsin."
```

## Client components

```tsx
import { useT } from "@/i18n/candidate-client";

const t = useT("intro");        // namespace is typed
t("start");                     // key is typed against candidate.tr.json
t("minutes", { count: 24 });
t.rich("resumeNote", { email, mail: (chunks) => <a href={...}>{chunks}</a> });
```

`useT` is typed against the dictionary rather than through next-intl's global
`AppConfig` augmentation. That global would have to be either the candidate
dictionary or the manager one, and this application renders both; typing the
namespace instead keeps a missing key a compile error on both sides.

## Server components and route handlers

```ts
import { candidateT } from "@/i18n/candidate";
const t = candidateT(locale);
t("header.preparing");
```

Route handlers use `message(locale, code)` from `@/lib/candidate-api`, and
`badRequest(ctx, code)` / `conflict(ctx, code)` which do the lookup themselves.

## Where the locale comes from

**Candidate side.** `assessments.locale`, set when the manager sent the
invitation. The candidate can override it with `?lang=en`, which is applied
once, written back to the assessment, and then stripped from the URL by a
redirect. So:

- a candidate invited in English opens the link in English, with no guessing
  from browser headers;
- the choice survives navigation without every link carrying a query parameter;
- `consents.locale` records the language the consent text was actually shown in.

The switch is offered only for the locales the template version was authored in
(`template_versions.locale_set`), and only in the page frame, not in the stage
bar: changing language halfway through an answer moves the ground under the
candidate.

**Manager side.** Not the same source, and it should not pretend to be. The
panel is a logged-in surface used by the same people every day, so the choice
belongs to the person. It is the `kademe-lang` cookie, read by `managerLocale()`,
falling back to `Accept-Language` only on the first render. A cookie rather than a
column on `users`: the preference is per browser, it survives a logout, and it
needs no migration. The switch is two words in the header, not a dropdown, and it
works before hydration because each locale is its own form.

## The provider

`<CandidateIntl locale>` is a **client** component. next-intl's server provider
reaches for a request-level i18n config, and the candidate locale does not come
from the request, it comes from the assessment the token resolves to. Looking
the dictionary up on the client also keeps it out of the RSC payload.

There is deliberately no `src/i18n/request.ts` and no `next-intl/plugin` entry
in `next.config.ts`. Add one only if a surface appears whose locale really is a
property of the request.

## Two traps worth knowing

**`lang` on the subtree.** The root document is `lang="tr"`. CSS
`text-transform: uppercase` follows the element's language, so an English kicker
under a Turkish root renders as "WRİTTEN ANSWER". Every candidate root element
carries `lang={locale}`; screen readers pick the right voice from the same
attribute.

**Do not uppercase database text.** Company and position names are plain `text`
columns, not bilingual, and uppercasing them follows the page language:
"Kıdemli" becomes "KIDEMLI" on an English page. Names render as they were typed.

## Checking the dictionaries

```bash
python3 - <<'PY'
import json
tr = json.load(open('src/i18n/messages/candidate.tr.json'))
en = json.load(open('src/i18n/messages/candidate.en.json'))
def keys(d, p=''):
    out = set()
    for k, v in d.items():
        out |= keys(v, f'{p}{k}.') if isinstance(v, dict) else {f'{p}{k}'}
    return out
print('only tr:', sorted(keys(tr) - keys(en)))
print('only en:', sorted(keys(en) - keys(tr)))
PY
```
